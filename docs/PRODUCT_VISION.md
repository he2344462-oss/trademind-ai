# TradeMind 产品愿景与北极星

本文档定义 TradeMind 的长期产品方向、真实性边界和决策准则。它回答“为什么做”和“最终要形成什么闭环”；当前实施顺序以 [`roadmap.md`](roadmap.md) 为准，实际完成状态以 [`PROGRESS.md`](PROGRESS.md) 为准。

## 产品定位

TradeMind 是面向小型电商经营者的 AI 驱动商品发现、选品、定价、铺货和经营反馈系统。

核心目标不是做一个孤立的采集器、AI 打分工具或重型 ERP，而是持续减少经营者在以下链路中的重复人工工作：

> 找货 → 判断值不值得卖 → 算成本 → 定价 → 制作商品内容 → 铺货 → 查看真实销售表现 → 调整经营策略

运营者只需配置经营边界和目标：

- 经营平台和商品类目
- 采购价格范围、默认采购地区和测试采购数量
- 最低利润、最低利润率和风险偏好
- 每日发现数量和每日测试商品数量

系统在这些边界内持续执行：

> Source Discovery → Source Product → Freight → Candidate → Pricing → Selection → Ranking → Human Approval → Catalog → Listing → Content → Assets → Ready Check → Publish Package / Authorized Publish → Performance → Calibration

发布、重大调价、账号授权、付款等敏感动作始终受权限、审计和人工门槛约束。

## 北极星目标

TradeMind 的北极星不是“采集数量”“AI 调用次数”或“生成了多少高分商品”，而是：

> **让经营者用更少的人工时间，持续完成更多有真实证据、可追溯结果的商品经营闭环。**

首要衡量指标是“每周完成真实经营闭环的有效测试商品数”：商品必须从合法来源发现，经过成本、证据、人工批准和铺货检查，并取得可关联的真实经营反馈。仅有 fixture、虚构市场数据或未回填结果的商品不计入。

同时使用以下护栏指标，避免为追求数量牺牲真实性和安全性：

- 单个测试商品所需的运营者人工时间
- 采购成本、运费、市场信号和销售反馈的真实数据覆盖率
- Prediction 与 Outcome 的可关联率
- 将 unknown 错误展示为确定值的次数必须为零
- 未授权数据访问、发布、付款或账号操作次数必须为零
- 实际利润、退款和规则校准结果只作为经营反馈，不用虚假承诺替代

具体数值目标应先建立真实基线，再由维护者人工确认；不得用测试数据设置看似漂亮的目标。

## 1. 自动商品发现

系统最终不能要求用户先具备完整选品能力。它应通过合法、授权或公开允许的数据来源主动发现商品。

第一阶段优先建设 1688 Source Discovery，支持关键词、类目、价格区间、起订量、供应情况、排除词和风险条件，并自动完成发现、去重、完整详情采集、Source Product 入库和 Candidate 创建。

其他货源通过 Provider 架构渐进扩展。尚未取得授权或无法合规访问的平台必须明确标记为未支持，不得通过 Cookie 注入、私有接口破解、验证码绕过或反风控手段伪装成可用能力。

## 2. 真实成本系统

Pricing 不能只看采购价，至少应考虑：

- SKU 采购成本和采购运费
- 包装成本
- 平台费用和支付费用
- 售后损耗与退货预留
- 其他固定费用和比例费用

金额使用精确 Money 模型。多 SKU 统一售价必须用最差风险 SKU 保护商品级利润；SKU 级结果仍需保留。未知成本必须标记为 `unknown`，不得默认按零元计算后再表现为确定利润。估算、包邮和已验证成本必须有不同状态，并保存来源、时间、适用地区、数量和证据。

## 3. 选品系统

Selection 必须是可解释、可回放、可测试的规则系统，不能表现为“AI 觉得这个商品 90 分”。结果至少拆分为：

- **Base Quality**：利润、供应、资料质量、基础风险和平台适配
- **Market Opportunity**：真实需求、竞争和趋势证据
- **Evidence Coverage / Confidence**：输入数据覆盖、来源等级、新鲜度和可信度

约束原则：

- `unknown` 不能通过动态重新归一化把总分抬高
- Demand 和 Competition 都未知时不能给出 Strong Recommend
- 市场数据覆盖不足必须降低推荐等级，并提示小规模测试
- Confidence 表示分析数据可信度，不是赚钱概率
- blocker、warning、推荐原因和缺失证据必须可追溯
- AI 只能解释结构化结果，不能决定分数、利润或 blocker
- 真实经营样本不足时禁止自动学习和自动修改权重

## 4. Ranking

批量发现数百个商品后，运营者最终只应重点查看 TOP N。Ranking 必须真正拉开普通商品与优秀商品的差距，并保存：

- 为什么排名靠前或靠后
- 哪些依据是真实证据
- 哪些数据缺失或过期
- 哪些数值是估算和假设
- 风险、利润、置信度和市场覆盖如何影响排名

Ranking Score 是批次内排序指标，不得覆盖商品本身的 Overall Score。

## 5. AI 边界

AI 可以解释、总结、生成标题和描述、提炼卖点、提出运营建议、识别异常和辅助分析。

AI 不得篡改或编造采购价、SKU、库存、运费、供应商、品牌、认证、销量、利润、发货承诺和平台事实。缺失事实应省略、标记待补充或交由人工确认，不得为了内容完整度制造事实。

所有 AI 能力必须可关闭、可降级、可审计。没有 AI Provider 时，规则分析和模板内容仍应正常工作。

## 6. 铺货

商品批准后进入以下受控流程：

> Catalog → Platform Listing → Content → Images → Pricing Snapshot → Human Review → Ready Check

没有官方平台写权限时，系统生成 public/internal 严格隔离、可供人工使用的 Publish Package。只有取得合法官方 API 授权后，才允许增加 Authorized Publish Provider。

关键发布动作必须具备权限、审计、幂等和人工门槛。系统不得通过浏览器模拟点击、私有接口、Cookie 注入或绕过平台控制实现所谓自动铺货。

## 7. 真实经营闭环

系统应把发布后的实际表现关联回 Listing、Content Version、Pricing Snapshot、Catalog、Candidate Analysis 和 Source Product，至少记录：

- 曝光、浏览、点击、收藏、咨询和消息
- 订单、销量、收入、退款、退货和售后
- 实际采购成本、实际运费、平台费用和实际利润

每个 Prediction 都应能够与 Outcome 比较。预计利润和实际利润必须在数据模型与 UI 中明确区分。

## 8. Calibration

系统需要持续回答：高分商品是否实际优于低分商品；某个评分维度、blocker 或 warning 是否与成交、利润和退款相关。

规则调整必须遵循：

> 生成 Suggestion → 人工 Review → 创建新 Selection Config → A/B 或历史回测 → 人工 Activate

历史 Analysis 保持原配置版本，不得被新规则重新解释。样本不足时必须显示 `insufficient_sample`，禁止自动调权或制造因果结论。

## 9. 自动化等级

- **Level 1：AI 辅助运营**。人主动发起大多数任务，系统负责计算、整理和提示。
- **Level 2：半自动运营**。系统定时找货、采集、分析、排序并生成待审核商品。
- **Level 3：受控自动运营**。低风险重复任务自动执行；发布、重大调价、账号、授权、采购和付款等敏感动作继续受权限与审批约束。

目标不是完全无人监管，而是把人的注意力集中到证据判断和高风险决策。

## 10. 真实性原则

> **Unknown stays unknown.**

- 系统不知道的数据必须明确说不知道
- fixture/test 数据不得进入真实经营指标
- 估算值必须标记 `estimated`
- 真实值必须保存来源、时间、新鲜度和证据
- 聚合结果必须能追溯到原始来源
- 不得为了让 Dashboard、评分或 AI 报告更好看而制造确定性

## 11. 可用性目标

普通运营者的日常工作不应要求写代码、执行 SQL、理解 Redis/Worker，或依赖 Codex 才能完成。开发环境最终应一键启动；生产环境应具备自动启动、健康检查、异常恢复、监控、备份和安全升级路径。

## 12. 产品边界

TradeMind 不主动扩展成重型完整 ERP。除非真实闭环证明必要，以下能力不作为当前优先事项：

- 复杂 WMS、OMS、多仓和财务结算
- 完整多租户、套餐计费和复杂组织权限
- 自动采购、自动付款和无人审批发布
- 未授权平台采集、私有接口和反风控能力
- 缺少来源的“AI 市场数据”或自动选品权重学习
- 与核心经营闭环无直接关系的大型功能

## 13. 决策准则

任何新 Sprint、功能、Bug 修复或架构任务开始前，先回答：

1. 它是否帮助 TradeMind 更接近上述核心闭环？
2. 是否已有模块可以复用？
3. 是否需要真实数据验证？
4. 是否会制造无法验证的“AI 能力”？
5. 是否增加日常人工步骤？如果增加，能否说明必要性？
6. 是否引入新的安全、隐私或平台合规风险？

优先修复真实 UAT 暴露的问题，其次开发当前路线上的闭环能力。架构优化必须服务明确问题，不以“更漂亮”为理由推倒重写。

## 14. 文档治理

- 本文档维护长期方向，非日常任务清单；重大定位调整必须由项目维护者人工确认。
- [`roadmap.md`](roadmap.md) 只维护 Now / Next / Later，并按真实验证结果调整。
- [`PROGRESS.md`](PROGRESS.md) 记录实际完成状态，不把规划写成已实现。
- Sprint 计划、Bug 修复和架构评审必须说明与本文档的关系；不相关的大型需求默认暂缓。
